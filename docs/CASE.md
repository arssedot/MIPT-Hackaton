# Соответствие кейсу и границы реализации

Цель MVP — провести эксперта от загрузки документа до объяснимого списка замечаний и отчёта. Цвет интерфейса взят из документа «Описание кейса для участников». Сам документ и выданные пары исходных/исправленных ТЗ в публичный Git не включены.

| Требование кейса                           | Реализация                                                               | Граница                                            |
| ------------------------------------------ | ------------------------------------------------------------------------ | -------------------------------------------------- |
| Текст, таблицы и структура                 | Абзацы и строки таблиц с разделами и id                                  | Без страниц Word, OCR, колонтитулов и сносок       |
| Привязка к документу                       | Точная цитата, основной и связанные блоки, переход в просмотре           | Устойчивость id в пределах одной проверки          |
| Разные категории проблем                   | Семь категорий, локальные правила и смысловой адаптер                    | Полнота локального режима ограничена               |
| Корректные фрагменты не помечаются ошибкой | Разделение confirmed/review, тест эквивалентности и совпадающих значений | Нужна отдельная оценка на независимом корпусе      |
| Объяснение и корректировка                 | Текст объяснения и рекомендации для каждого замечания                    | Автоправка DOCX отсутствует                        |
| Проверяемые источники                      | Ограниченный каталог официальных ресурсов                                | Нет автоматически актуализируемой нормативной базы |
| Не выдумывать основания                    | Источники по allowlist, проверка цитат, отклонение невалидного ответа    | Ссылка на каталог не доказывает нарушение          |
| Разные предметные области                  | Универсальный prompt с блоками, синтетические примеры двух областей      | Без модели часть правил предметная                 |
| Ошибки файлов                              | Ограничения размера, повреждений, формата, UTF-8 и текста                | DOCX с изображениями без текста требует OCR        |
| Docker и воспроизводимость                 | Многостадийная сборка, Compose, миграция, README                         | Docker Desktop должен быть запущен                 |
| Архитектура и use cases                    | ARCHITECTURE.md и два сценария README                                    | Внешняя модель требует ключа владельца             |

## Работа с предоставленными примерами

Исходные и исправленные DOCX изучены как описание ожидаемых задач: несогласованные характеристики, события начала гарантии, состав комплектов, уточнение классификации и нормативных ссылок. Они не используются как программный словарь ответов, не загружаются в базу автоматически и не встраиваются в публичные демопримеры.

Публичные демонстрационные тексты написаны отдельно. Для независимой оценки следует сформировать набор документов вне выданных примеров и разметку экспертов. Не публикуются выдуманные показатели precision/recall или проценты покрытия кейса: пока нет проведённой экспертной оценки и достаточного корпуса.

## План развития

Первый приоритет — настроить выбранного провайдера, провести проверку обеих пар DOCX и отметить пропуски, ложные срабатывания и непроверяемые основания. Следующий — формализовать позиции и характеристики, чтобы не смешивать параметры разных изделий и отличать старое оборудование от нового.

Для нормативного анализа нужен поддерживаемый корпус: источник, редакция, дата действия, область применения и точная выдержка для конкретного вывода. На этой базе можно строить retrieval и проверку утверждений. Отдельно требуется определение режима закупки; нельзя автоматически применять все правила 44-ФЗ к каждой закупке.

После подтверждения качества: отдельные пользователи и права, очередь с повторяемыми заданиями, версии документа и сравнение результатов, экспорт исправлений DOCX, аудит решений, резервное копирование по расписанию и наблюдаемость. OCR добавляется при наличии реальных сканированных документов.
